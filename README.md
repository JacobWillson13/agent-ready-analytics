# agent-ready-analytics

Data agents can write SQL. They can't infer your business rules. This project measures how much a
documented, governed context layer changes a data agent's accuracy, cost, and latency, using a full
analytics stack (BigQuery, dbt, MetricFlow, LangGraph, LangSmith) and an eval suite scored against an
independent answer key.

**Result:** the same agent goes from 76% to 100% accuracy (50% to 100% on held-out questions) when it
gets the context layer, while using about a quarter of the tokens and a third of the latency.

> **All company data is synthetic.** Lanternfly Labs is a fictional developer-tools SaaS company. Its
> data is generated by a seeded simulation in this repo; none of it describes a real company. The PyPI
> download and GitHub release data is real.

## The setup

Lanternfly Labs sells an LLM observability platform through three motions: a free Developer plan, a
self-serve Plus plan ($39 per seat plus usage overage, billed monthly), and sales-led enterprise
contracts with cloud, hybrid, and self-hosted deployments. That mix creates the problems real SaaS data
teams deal with: revenue split across two billing systems, multi-year contracts, product telemetry that
only covers some deployments, and a CRM that lags reality.

The simulation covers January 2024 to October 14, 2026: about 80k orgs, $36.2M ARR, 6,048 paying
customers, 251 enterprise accounts. It plants 13 realistic data traps, each with a defense somewhere in
the context layer, and writes an answer key straight from simulation state so evals never grade the
models against themselves.

## Results

Same agent (Claude Sonnet 5.5 via LangChain `create_agent`), same questions, three levels of context.
25 core questions x 3 runs, plus 6 held-out questions written after the business guides. Answers are
scored in code against the answer key.

| Context level | Core accuracy | Holdout accuracy | Tokens / question | Cost / question | p50 latency |
|---|---|---|---|---|---|
| raw tables only | 76% | 50% | 51.7k | $0.130 | 27.5s |
| dbt models + docs | 100% | 100% | 13.9k | $0.035 | 11.2s |
| full context | 100% | 100% | 13.7k | $0.033 | 9.9s |

What this shows:

1. **Context fixes business-rule errors, not data-hygiene errors.** The raw-table agent handled
   duplicates, internal usage, soft deletes, and the self-hosted telemetry gap on its own. It failed on
   rules that exist only in the business: self-serve revenue lives outside the CRM (0% on that trap),
   enterprise prepay invoices double count ARR (0%), and ARR is a balance that must not be summed across
   months (0%). The held-out questions confirm it: raw dropped to 50% on new wording, context stayed at 100%.
2. **Modeling and documentation carry most of the accuracy.** dbt docs alone reached 100%, because the
   marts already encode the hard rules and the column docs explain the rest. Agents raise the value of
   good data modeling; they don't replace it.
3. **Context makes the agent cheaper and faster, and evals keep it that way.** Raw spends about 4x the
   tokens and nearly 3x the latency to reach worse answers. A first version of the full-context prompt
   matched docs-only accuracy but cost about 70% more tokens; the eval caught it, and
   [PR #1](https://github.com/JacobWillson13/agent-ready-analytics/pull/1) fixed it.

### Context changes are evaluated like code

[PR #1](https://github.com/JacobWillson13/agent-ready-analytics/pull/1): traces showed the full-context
agent listing metrics and reading a guide before nearly every question. The fix injected a compact index
of governed metrics and guides into the prompt, made guides read-on-demand, and filled four missing metric
descriptions the index exposed.

| Full context | Accuracy | Holdout | Tokens / question | Cost / question | p50 latency |
|---|---|---|---|---|---|
| Before | 100% | 100% | 24.0k | $0.056 | 14.5s |
| After | 100% | 100% | 13.7k | $0.033 | 9.9s |
| Change | held | held | -43% | -41% | -32% |

[PR #3](https://github.com/JacobWillson13/agent-ready-analytics/pull/3) automated the loop. Every PR runs
`dbt build` (tests, unit tests, and reconciliation against the answer key) and MetricFlow validation. A PR
that touches context (model YAML, doc blocks, guides, agent prompts) also runs the full-context eval and
posts accuracy, tokens, cost, and latency against the committed baseline as a PR comment. PRs that don't
touch context skip the eval.

### Caveats

- The company and its data are synthetic, and the same person wrote the traps, the guides, and the
  questions. The held-out set reduces, but does not remove, that bias.
- 31 questions and one model. Enough to show the direction and size of effects, not a benchmark.
- On this question set, guides and the semantic layer add governance (one definition shared by the agent,
  dashboards, and MCP clients, reviewed through CODEOWNERS) and efficiency, but not measured accuracy over
  docs alone. Questions that need cross-model business rules would separate them further.

## Stack

| Layer | Tool |
|---|---|
| Synthetic sources | Seeded Python generator: Salesforce, product DB, Segment, Metronome, support desk |
| Real sources | PyPI downloads (BigQuery public dataset) and GitHub releases (dlt) for the open-source packages the fictional product builds on |
| Warehouse | BigQuery |
| Modeling | dbt Core 1.12: contracts, unit tests, incremental Segment model, SCD2 snapshot, exposures |
| Metrics | MetricFlow, dbt 1.12 Semantic Layer spec (annotations next to each column) |
| Business context | `guides/*.md`, versioned and code-owned |
| Trust signals | `meta.endorsed` on marts, gated by CODEOWNERS |
| Agent | LangChain `create_agent` on LangGraph; CLI and MCP server |
| Observability and evals | LangSmith tracing and experiments; GitHub Actions runs dbt and the context eval on PRs |
| Dashboard (optional) | Self-hosted Lightdash, see `lightdash/` (SQL Runner on marts; MetricFlow stays the only metric definition) |

## How it flows

1. `generator/` simulates 33 months (2024-01-01 to 2026-10-14) and writes raw parquet plus an answer key.
2. `scripts/load_bq.sh` loads raw tables into `raw_*` datasets and the answer key into `eval_truth`.
3. `ingest/` pulls real PyPI and GitHub data.
4. dbt builds staging, intermediate, and endorsed marts, then runs tests, including reconciliation
   tests that compare marts to the answer key.
5. The agent answers questions with tools that read dbt docs, endorsements, guides, and metrics.
6. `evals/` asks 25 core and 6 held-out questions at three context levels, scores them in code, and
   records each run as a LangSmith experiment.
7. CI runs steps 4 to 6 on pull requests (`.github/workflows/ci.yml`).

## Context levels

| Level | Agent can see |
|---|---|
| raw | Raw source tables only |
| docs | dbt models and their documentation (no endorsements, guides, or metrics) |
| full | Everything in docs, plus endorsement ranking, governed metrics via MetricFlow, business guides, and a compact index of metrics and guides in the prompt |

Each golden question is tagged with the traps it exercises (total contract value vs ARR, stale CRM
status, self-hosted telemetry gap, upgrade is not churn, and others), so results break down by trap.
See `docs/DATA_GENERATION_PLAN.md` for the full trap list.

## Run it

```
uv sync
cp dbt/profiles.yml.example ~/.dbt/profiles.yml        # reads the project from $GCP_PROJECT
gcloud auth application-default login
# set the variables in .env.example (keep real values outside the repo), including DBT_PROFILES_DIR

make generate            # ~3 min, ~320 MB parquet
make load GCP_PROJECT=$GCP_PROJECT
make ingest GCP_PROJECT=$GCP_PROJECT   # scans ~300 GB of the public PyPI dataset; run the dry run first
make build               # dbt build + semantic validation
make golden              # answer key -> evals/golden.jsonl (always rebuild after generate)
make agent Q="What was total ARR at the end of September 2026?"
make evals               # raw vs docs vs full in LangSmith
uv run python evals/run_evals.py --split holdout --levels raw docs full
uv run python evals/experiment_stats.py evals/results/*.json   # tokens, cost, latency per level
make baseline            # commit evals/baseline.json for CI
make lightdash
```

Use `--scale 0.05` on the generator for fast iteration.

## Credentials

Two service accounts, least privilege:

- `ara-ci` builds models and runs the reconciliation tests, so it can read and write every dataset,
  including the answer key in `eval_truth`.
- `ara-agent` runs the agent in CI (and Lightdash). It has read access to every dataset except
  `eval_truth`, granted per dataset with `GRANT roles/bigquery.dataViewer ON SCHEMA ...`. The agent's
  SQL tool also enforces a dataset allowlist per context level, so the answer key is blocked twice.

CI reads both keys from GitHub secrets. A production setup would use Workload Identity Federation
instead of JSON keys.

## Background

The architecture follows patterns data teams have published about running agents on their warehouse,
in particular LangChain's write-up
[How we built LangChain's agent-first data stack](https://langchain.com/blog/agent-data-stack) and
Hex's [LangChain customer story](https://hex.tech/customers/langchain/): rich dbt definitions, a semantic
layer for metrics, written business guides, endorsement signals, and observability feeding a context
improvement loop. Their stated next step was evaluating whether context changes actually improve agent
answers; this project builds that evaluation and runs it in CI. Lanternfly Labs is fictional, and none of
its numbers are estimates of any real company.
